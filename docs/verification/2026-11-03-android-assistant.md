## 반영된 동작

- 빠른 설정 타일에서 작은 텍스트·음성 선택창을 연다. 선택만으로 녹음을 시작하지 않는다.
- 한국어 기본 문법으로 일정 입력과 한 시간 이동을 해석한다. 제목·날짜·시간·반복을 확인하고 저장한다. 지원되지 않는 표현은 직접 지정할 수 있다.
- 앱, 입력창, 다음 일정 위젯, 오늘 일정 위젯이 같은 기기 내 SQLite 데이터를 사용한다.
- 홈은 오늘 일정과 다음 일정을 표시하고 저장된 내용으로 즉시 브리핑을 만든다. 지원 기기에서는 사용자가 요청한 전면 화면의 Nano 요약을 추가로 사용할 수 있다.
- 월말·윤년 반복은 원래 기준일과 시간대를 유지한다. 알림은 변경·재부팅 시 복원하고 오래된 예약의 중복 실행을 막는다.
- Firebase 기존 원본은 같은 계정에서 읽기 전용으로 복구한다. 설정을 먼저 복구하며 새 로컬 선택을 보존한다. 실패한 이전은 재시도할 수 있고 로컬 사용을 막지 않는다.
- 외부 날씨·뉴스·주식은 선택 후 명시적으로 요청한다. 로컬 일정 내용을 외부 AI로 자동 전송하지 않는다.

## 실제 에뮬레이터 확인

Android 10 / API 29, x86_64 AOSP, Asia/Seoul. 캡처 화면은 720 × 1600, density 280이다. 모든 화면은 설치된 앱과 실제 시스템 타일·런처 위젯을 캡처했다. 생성하거나 합성한 화면이 아니다. 일정은 모두 테스트용 예시다.

| 흐름 | 확인 내용 |
|---|---|
| 빠른 설정 | 시스템 패널의 실제 타일을 누르면 텍스트·음성 선택창이 열림. API 29 타일 배치는 테스트 기기의 시스템 명령으로 추가 |
| 텍스트 입력 | 오늘 15시 팀 회의, 오늘 18시 운동, 내일 09시 프로젝트 점검을 실제 입력창에서 저장 |
| 일정 변경 | 팀 회의 15→16시, 위젯의 입력 버튼에서 16→15시 변경 전후 확인 후 저장 |
| 위젯 갱신 | 실제 런처 확인창에서 두 위젯 배치. 저장 직후 오늘 일정 위젯이 16시에서 15시로 갱신됨 |
| 데이터 지속성 | APK 업데이트 및 앱 재실행 후 홈·캘린더·두 위젯에 동일한 데이터 유지 |
| 다음 날 일정 | 캘린더 11월 4일에서 프로젝트 점검 09시 확인 |
| 여러 변경 대상 | 같은 제목의 일정 두 개를 실제 생성하여 선택창의 두 후보·취소 확인. 취소 시 임의 변경하지 않음. 이후 이전 예시만 삭제해 최종 예시 세 개 유지 |
| 음성 시작 제어 | 음성 선택 직후 RECORD_AUDIO app-op 사용 내역 없음. 별도 시작 버튼 필요 |
| 미지원 안내 | 시작 버튼을 누르면 기기 내 음성 미지원과 텍스트 대안을 안내. Nano 미지원 상태에서도 로컬 브리핑·입력 사용 가능 |

실제 일정 알림은 15시·18시에 전달됐다. 18시 운동 알림은 실행 중인 앱에서 해당 상세 화면으로 이동했다. 실제 Android 시스템 알림 설정을 끄고 복귀하면 ‘허용 필요’, 다시 켜고 복귀하면 ‘허용됨’으로 바뀌었다. Android 10에서 raw AppOps만 바꾸는 방법은 실제 알림 설정 차단과 달라 최종 권한 검증 방법으로 사용하지 않았다.

기기 시간만 테스트 목적으로 다음 날 07:59:30으로 이동한 뒤 실제 08:00 알람을 실행했다. ‘오늘의 일정 1개’, ‘09:00 프로젝트 점검’ 알림이 전달됐고, 실제 알림을 누르면 홈으로 진입했다. 테스트 후 기기 시간·자동 시간·알림 허용 상태를 원복하고 매일 08:00 예약을 재설정했다.

`5e1d296`의 콜드 Activity/React UI 진입에서는 일정 URI가 전달됐음에도 홈으로 이동하는 문제가 발견됐다. SDK54 Expo Router의 150ms 초기 URL 대기와 로컬 시작 시 탐색기 마운트 시점, Android의 기존 Intent 보존을 함께 보완했다. Stack을 유지하고 준비 완료 후 직접 읽은 초기 URL을 한 번 재적용하며, 새 유효한 앱 링크는 이전 요청을 무효화한다. MainActivity의 `setIntent`는 지속되는 설정 플러그인으로 React 위임 전에 실행한다. 추가 회귀 검사와 한정 코드 검토는 통과했다.

`2fab494` 설치본의 실제 알림 재검증에서는 팀 회의 알림을 누른 뒤 팀 회의·2026-11-03·15:00이 표시된 일정 상세 화면으로 진입했다. 증거는 `tooling/native-acceptance/final-2fab494/04-cold-landing.png`와 같은 디렉터리의 알림·Activity·로그 기록이다. 빠른 설정 패널에서 네이티브 TileService가 다시 연결되어 클릭 직전 PID가 존재했으므로, 이 검증은 Activity/React UI 초기 진입 검증이며 전체 네이티브 프로세스가 없는 상태의 검증으로 확대 해석하지 않는다.

후속 검토에서 초기 Settings 링크를 오래된 Expo 알림 응답이 덮는 별도 조건을 발견했다. `5f10fd0`은 유효한 앱 내부 초기 링크가 있으면 이전 응답을 읽지 않도록 수정했다. 새 회귀 검사는 수정 전에 실패했고 수정 후 전체 Node 50개, TypeScript, 앱 범위 ESLint와 공백 검사가 통과했다. 독립 한정 검토도 승인됐다. 이 마지막 변경은 자동 검사로 검증했으며 APK 재패키징·에뮬레이터 재설치를 수행한 것으로 기록하지 않는다.

## 검토와 범위

네이티브 저장·예약, 입력 수명주기, 앱 이전·시간대 처리를 각각 검토했다. 전체 변경 검토에서 나온 네 가지 중요 항목과 세 가지 보완 항목은 모두 수정했다: 오래된 AI 응답 차단, 원래 계정의 알림 설정 복구, 알림 URI, 실제 시스템 알림 허용 상태, 위젯 경계 갱신, 복귀 시 AI 상태 갱신, 1년 이후 다음 일정 탐색.

마지막 한정 재검토에서 발견한 위젯 파일 잘림과 동시 갱신 순서 문제도 수정했다. 최종 코드 `5e1d296`의 재검토 결과는 범위 내 미해결 Critical·Important·Minor 0건이다. 이후 실제 Android 컴파일과 위 계측 검사도 통과했다.

후속 실제 콜드 진입 실패는 별도 한정 수정·검토로 처리했다. 그 과정에서 발견한 ‘늦은 초기 일정 링크가 새로운 Settings 링크를 덮는’ 경합도 회귀 검사와 함께 수정했다. `2fab494`의 이 수정 범위 검토는 승인됐으며, 실제 기기 재검증과 소스 검토 결과를 구분한다.

에뮬레이터에서 두 번째 위젯을 배치할 때 테스트용 UiAutomation의 Android 10 접근성 캐시 스레드가 시스템 AppWidgetService의 null provider 때문에 중단됐다. 스택은 시스템 접근성·위젯 코드였으며 앱 코드 프레임은 없었다. 자동화를 끈 정상 앱 재실행 후 두 위젯 모두 바인딩·데이터 표시를 확인했다. 이 테스트 환경 실패를 실제 음성·AI 또는 접근성 품질 검증으로 해석하지 않는다.

## 남아 있는 실기기 검증

- 지원되는 실제 기기에서 한국어 오프라인 음성 인식과 Gemini Nano 출력 품질·성능·모델 다운로드를 확인해야 한다. 이 에뮬레이터의 미지원 안내를 실제 인식 성공으로 표시하지 않았다.
- 백그라운드 전환 시 오래된 응답은 앱에서 폐기한다. 실행 중 AICore 추론의 실제 중단까지 확인한 것은 아니다.
- Android 13 이상 타일 추가 대화상자, Android 14 이상 타일 PendingIntent, PIN 잠금 해제, 제조사별 절전·런처, TalkBack·큰 글꼴은 해당 기기에서 추가 확인이 필요하다.
- 실제 운영 Firebase 계정의 이전 및 외부 브리핑 백엔드 실행은 이번 에뮬레이터에서 검증하지 않았다. 이전의 실패·재시도·계정 일치·새 로컬 설정 보존은 자동 회귀 검사로 확인했다.
- 위젯의 다음 일정·자정 갱신은 기기를 깨우지 않는 일반 알람과 주기 갱신을 사용하므로 절전 중 지연될 수 있다.
- 로컬 데이터의 다른 기기 동기화나 앱 삭제 후 자동 복원은 이번 범위에 포함되지 않는다.
